# Additional repository checks

RepoMan registers deterministic checks in Issues and Settings. The dashboard may fetch remote-tracking refs and read GitHub metadata; the shared CLI fetches remote-tracking refs only with `--fetch` and reads GitHub metadata only with `--remote`. Neither installs packages, runs project scripts, changes working files or publishes anything. Checks and repository-owned exceptions are shared through RepoManCore; see [the CLI contract](issues.md#shared-cli).

Optional access files, naming policies and absent Actions workflows report **not applicable** when out of scope. Notebook hygiene reports **skipped** until enabled, then **not applicable** if no notebooks exist. Required missing inputs remain findings or incomplete.

Dependency checks return **not applicable** when no supported manifests are present; they do not validate Swift or other unsupported ecosystems. Missing or unreadable tracked inputs remain **incomplete**, with the repository-relative path in their diagnostics.

Routine CI coverage excludes literal false job/step conditions and jobs depending on disabled jobs. Unevaluated conditions, missing dependencies and dependency cycles stay incomplete when no independent unconditional validation is recognized. Trigger filters and shell control flow are not fully interpreted.

## CI components and expected jobs

`ci.coverage` assesses every detected Python, JavaScript and Swift component separately, matching literal workflow/job/step working directories and recognizable commands. The `uv run --config-file` option accepts a literal path in separated or equals form, including quoted paths without shell operators or escapes; a missing argument does not count as validation. Native `node --test` counts as JavaScript test validation; echoed commands and reporter/name-pattern options alone do not. Direct literal `python`, `python3` or version-qualified Python commands can count as test validation when a tracked script declares an undecorated `unittest.TestCase` with test methods and a final guarded `unittest.main()` call. This bounded subset requires an unconditional same-repository checkout of the current revision at the workspace root, a matching component working directory, static standard-library imports, and supported literal module setup. RepoMan parses at most 256 KiB per script with isolated system `/usr/bin/python3` (`-I -S -B`), a three-second deadline and no inherited credentials; it never executes repository Python. It checks import-shadowing paths and caches at most 32 script inspections per coverage check. Missing Python, custom imports/setup, help or extra arguments, `load_tests`, skipped/decorated tests, suppressed exits, tolerated workflow failures, nonstandard shells, unsupported checkout layouts and ambiguous syntax remain incomplete. Structural recognition establishes a test invocation, not test quality or runtime success. Default coverage requires one routine validation per component; `.repoman.json` can require explicit `test`, `build`, `lint` and `typecheck` categories. Repository policy may also describe generic components. Supported unconditional jobs and dependencies count; disabled jobs do not. Dynamic directories, custom wrappers, unknown conditions and unsupported syntax remain incomplete, preserving known missing-component findings.

`ci.expectedChecks` is an opt-in remote check. It verifies each published branch commit against declared job names and optional workflow, event and publisher identities. Missing jobs and unexpected skipped/neutral results need attention; pending, ambiguous or unavailable identities stay incomplete. Failed jobs remain visible through `ci.failing`. The default accepted conclusion is `SUCCESS`; repositories can explicitly accept `SKIPPED` or `NEUTRAL` for jobs where nonexecution is intentional. Failure conclusions cannot be accepted. CI status reads are shared within one inspection.

```json
{
  "version": 1,
  "ci": {
    "components": [{"path": ".", "ecosystem": "swift", "requires": ["test", "build"]}],
    "expectedChecks": [{"name": "check", "workflow": "Repository checks", "event": "push", "app": "github-actions"}]
  }
}
```

Component paths must be literal repository-relative paths. Ecosystems are `python`, `javascript`, `swift` or `generic`. At most 64 components and 64 expected checks are supported. Duplicate identities, unknown fields and invalid conclusions make verification incomplete. This policy does not change GitHub branch protection or execute project commands.

Dependency inspection includes root manifests and tracked nested manifests, inheriting ancestor settings and lockfiles. Workstation configuration cannot substitute for repository-owned safeguards.

Inspection allows at most 64 groups, 32 include levels and 4096 expanded declarations; malformed, missing or cyclic includes remain incomplete. This verifies declared metadata, not resolution or the transitive dependency graph.

## Dependency release-age comparisons

`dependencies.releaseAge` compares the current working-tree locks, including unignored untracked files and unstaged deletions, with the exact Git object selected by `--base`. The base is never inferred. Git replacement objects and automatic lazy fetches do not alter base inspection. No checkout, resolver, installation, index update or credential injection is performed. `--remote` permits anonymous HTTPS reads from the public npm and PyPI registries; GitHub credentials are not forwarded.

JSON schema 3 has an optional additive `dependencyComparison` field: base commit, candidate HEAD, working-tree inclusion, fixed observation time, SHA-256 hashes for inspected inputs, and introduced version evidence. Each entry records whether its version or origin changed, lockfile paths, registry URL, publication and eligibility times, status, risks, unknown evidence and any applied age exception. Timestamps preserve microseconds, with submicrosecond publication evidence rounded upward. Candidate manifests and workspace configuration are included in the input hashes; lock coverage reuses the shared ecosystem-specific declared-workspace lookup. Candidate HEAD, relevant path inventory and inspected bytes are revalidated after registry reads; changed inputs remain incomplete. An empty introduced set proves only that these supported lock inventories add no version identities. Other checks still own manifest/lock consistency, source policy, audits and runtime compatibility.

npm public tarballs must match the version's public metadata; locked digests must match when present. pnpm integrity-only entries must match the public version digest. uv public registry entries are normalized by Python package name; local roots and declared workspace members are excluded only after their manifests and membership are verified. Supported workspace declarations use literal paths and single-component `*` patterns; external paths or ambiguous workspace layouts remain incomplete. Missing/malformed inventories or registry evidence never become empty successful comparisons. PyPI takes the latest artifact upload timestamp and retains yanked-file risk. Unchanged baseline entries are outside this introduced-version comparison; changed source identities, explicit artifact URLs and comparable digests are rechecked even when the version text is unchanged. Known violations survive incomplete evidence elsewhere.

Only an explicitly approved exact-version `exceptions.dependencies.releaseAge` subject ending in `#age` can suppress a proven young-version finding. The checker records the applied reason but cannot authenticate human intent: review authorization separately. Wildcards, risk exceptions, unknown sources and missing evidence cannot bypass the gate. Deprecated/yanked releases remain blocked independently of age exceptions. Ordinary runs without an explicit base report this comparison as skipped, not passed.

Inspection allows 128 lockfiles per side, 1 MiB per text input, 20,000 Git paths, 2,048 introduced identities, four concurrent registry reads, 20 seconds per request, 64 MiB per response and a 180-second scheduling deadline. Metadata is reduced to verdicts and discarded, not stored in a persistent cache. API failures, limits, unsupported schemas or absent prerequisites remain incomplete. Supported formats do not cover other lock ecosystems or prove the age of dependencies absent from those inventories. Registry contracts: [npm package metadata](https://github.com/npm/registry/blob/main/docs/responses/package-metadata.md) and [PyPI JSON API](https://docs.pypi.org/api/json/).

## Repository configuration

An optional root `.repoman.json` controls new-check thresholds and precise exceptions. The existing Ignore Check action and global Settings toggles also remain available as display preferences.

```json
{
  "version": 1,
  "stashAgeDays": 60,
  "maximumTrackedFileBytes": 10485760,
  "notebooks": {
    "enabled": true,
    "maximumOutputBytes": 262144
  },
  "exceptions": {
    "dependencies.lockfile": {
      "pyproject.toml": "This library intentionally tests fresh dependency resolution."
    },
    "dependencies.sources": {
      "pyproject.toml": "The documented GPU wheel index is approved for this project."
    },
    "notebooks.hygiene": {
      "lessons/expected-error.ipynb": "This lesson demonstrates the exception intentionally."
    }
  }
}
```

Exceptions map a check ID and exact finding subject to a nonempty reason; subjects are matched literally and wildcards do not expand. No executable configuration is accepted. Manifest, documentation, notebook and generated-file subjects are repository-relative paths. Workflow subjects are `.github/workflows/<name>.yml`. Stash subjects are full stash commit hashes. Branch health subjects are full `refs/heads/<branch>` refs. Checkout-integrity subjects are repository-relative paths. Runtime and lockfile-drift subjects are manifest paths. Project-reference subjects are manifest or workflow paths. Git operation subjects are `conflicts`, `HEAD`, or the Git marker name. Metadata subjects are `owner/repository`.

Changing a repository exception changes the detector's policy, and can verify a finding as absent under that policy. Global display toggles and Ignore Check do not change verification. Inspect the recorded reason when reviewing a policy-based resolution.

Unknown configuration fields, unsupported versions, empty exception reasons and out-of-range thresholds make the new checks unavailable. `stashAgeDays` accepts 1–3650; notebook output limits accept 1024–8388608 bytes. `maximumTrackedFileBytes` accepts 1024–1073741824 bytes (default 10485760). Missing fields retain defaults; notebook checks default to disabled until a repository opts in.

## Native Swift inspection boundaries

SwiftPM support requires a literal top-level `let package = Package(...)` (or `var`) and literal arrays for products, targets and dependencies. Supported Git dependency requirements are `from`, exact, branch, hexadecimal revision prefixes and stable numeric ranges. Xcode reads OpenStep/XML property lists and active project package/target references; source paths use supported group or source-root trees. Resolved versions support three-part stable versions, valid Git revisions and matching locations.

Conditional/computed manifests, registry declarations, prerelease version comparisons, dynamic or absolute project paths and unsupported property-list graphs remain incomplete. If a separate external `.xcworkspace` might own an absent project resolution file, RepoMan requests manual workspace review instead of asserting a missing lockfile. Transitive dependency resolution, package trust and compiler compatibility remain the responsibility of normal tooling and CI. These checks never fetch packages or execute Swift/Xcode.

## Published metadata

The visibility check uses a separate read-only GraphQL query with the existing GitHub CLI login, so it works without a README or published default branch. Background refresh may reuse visibility for ten minutes, keyed by owner/repository. Forced checks read fresh visibility. Missing visibility, authentication failures and API errors remain unavailable. RepoMan never changes visibility; update GitHub settings yourself when required.

The metadata check uses the installed GitHub CLI and its existing login. A read-only GraphQL request discovers the actual root README filename; a second request returns the description and that README together from the latest default-branch commit. All root README variants recognized by RepoMan are supported. Repositories without README files or tagline markers are skipped. It does not copy credentials or change descriptions during refresh.

Tagline validation follows the existing push-sync header contract: exactly one marker pair inside the opening centered paragraph, containing one plain-text `<strong>` element. A logo is an editorial choice and is not required to extract or compare the marked description. Invalid markers or unsupported HTML entities remain unavailable. The normalized tagline must be nonempty and at most 350 Unicode code points. Authentication failures, API errors, binary/unreadable READMEs and missing default branches cannot resolve existing metadata findings. RepoMan never changes descriptions or Actions automation; make those changes in your own tools.

## Inspection bounds

Checks continue to run off the UI actor in batches of at most four, sharing bounded file and Git reads within an inspection. Normal text files are limited to 1 MiB and the shared text cache to 32 MiB. Notebook files allow at most 8 MiB each, 32 MiB total, and 250 tracked notebooks. Git output is capped at 2 MiB, matching tracked paths at 20000 (Git path filters avoid enumerating unrelated source files), manifests at 64, documentation files at 100, and workflow directory entries at 200. Stash inspection permits at most 100 stashes and 20 old stashes. Excesses remain unavailable.

Read-only Git commands disable optional index writes and fsmonitor hooks and external diff/textconv helpers, time out after ten seconds and terminate with a bounded kill fallback. GitHub reads use the existing 15-second timeout and 2 MiB response limit. Inspection findings are cached by the existing refresh reports; changing selection does not rerun these checks. Startup and the minute scheduler run missing or expired checks; manual refresh forces fresh checks. Ordinary refresh reuses GitHub description metadata for at most ten minutes, keyed by the actual remote owner/repository, to limit API traffic across large repository collections. Forced dashboard refresh and CLI inspection bypass that cache. Reports explicitly track cached checks, and cached absence cannot resolve an earlier issue during ordinary refresh.

All-tracked-file checks share the 20000-path bound. Binary/text detection reads at most an 8 KiB sample per uncached file, with a separate shared 32 MiB sampling budget; decoded text still shares the 32 MiB cache. Oversized text, missing tracked files, escaping symlinks and unreadable files remain unavailable. Branch inspection permits at most 64 local branches. Workspace/reference expansion allows at most 256 visits, eight levels and 200 directory entries per read.

Refresh fetches every configured remote, even without a current-branch upstream, and prunes deleted remote-tracking branches. Explicit refspecs and an empty configured refmap restrict writes to `refs/remotes/<remote>/`; local branches and tags are preserved, including repositories with mirror-style fetch configuration. Submodule recursion is disabled. At most sixteen remotes are fetched sequentially within the existing shared 45-second deadline per repository. Any failure keeps remote-dependent findings unavailable.

Bun text lockfiles are read as JSONC, including comments and trailing commas. Bun safeguards use configuration beside the selected lockfile, or the workspace install root when no lockfile exists; standalone nested projects do not borrow unrelated ancestor policy. Bun’s built-in trusted-package list still permits some dependency lifecycle scripts, so the check requires explicit script suppression or a documented exception. Global workstation configuration is not inspected. These are static declaration checks; they do not resolve packages or validate the entire transitive graph. See [Bun configuration](https://bun.sh/docs/runtime/bunfig), [lifecycle scripts](https://bun.sh/docs/pm/lifecycle), and [text lockfiles](https://bun.sh/blog/bun-lock-text-lockfile).

### Safe CI failure locations

`ci.failing` includes bounded file/line/rule metadata from the owned secret-scan
annotation protocol documented in `.github/SECRET_SCANNING_REVIEW.md`. It never
requests annotation messages, raw details, source snippets or job logs. Unknown
annotation formats are ignored and truncated location lists are disclosed. A
failed job remains a finding even when it has no supported annotations.

## Current-lock advisory evidence

`dependencies.vulnerabilities` sends only verified public package names, exact versions and ecosystem names to OSV. Registry metadata is read anonymously from npm/PyPI; requests have no credential or cookie storage, follow no redirects and have bounded response sizes. No manifests, lockfiles, repository identities or private source URLs are uploaded. Public-registry verification failing does not cause a fallback to querying an unverified identity.

The complete supported inventory is distinct from an introduced-version age comparison and from GitHub's published dependency graph. npm alias/transitive copies are grouped by real package/version; uv names use Python normalization. Known matches survive malformed other locks, provider failures and changed inputs. Advisory IDs and details must agree on the package; aliases deduplicate findings, while verified withdrawals are retained as evidence. Unavailable details are unknown, not invented findings or clean results. Findings do not establish installed/deployed versions or reachability.

Bounds are 128 locks, 20,000 parsed entries, 2,048 distinct versions, four concurrent requests, a 180-second scheduling deadline, 20 seconds per in-flight request, 100 queries per batch, eight pagination rounds, 4,096 matches per batch and 4,096 advisory details overall. Locked source parsing uses the shared 1 MiB per-lock limit. Registry responses are limited to 2 MiB and OSV responses to 8 MiB. Reaching a bound remains incomplete. Advisory evidence is bound to HEAD and SHA-256 input hashes and rechecked for changes before completion; rerun after edits. A clear OSV result does not replace project-required native audits or security review.

Direct npm bundle members with `inBundle: true` and no standalone source record are eligible only when their nearest literal public parent declares them. Parent version metadata, public tarball and SHA-512 must match the lock; archive bytes must match that digest, and regular parent/member `package.json` files must establish the declared names, versions and bundle membership. The child must also exist under that identity in the anonymous public registry before OSV receives it. Private parents, undeclared members, links, extended/ambiguous tar forms, malformed metadata and mismatches remain incomplete. Known standalone-copy findings survive unsupported bundled copies. This verifies public embedded version claims, not byte-for-byte equivalence with a standalone distribution or exploitability.

Bundle limits are 16 parent archives, four concurrent verifications, 16 MiB compressed and 64 MiB expanded per archive, 10,000 members and 64 KiB per selected metadata file, within the advisory inspection deadline. Gzip CRC/framing and tar header checksums are validated; duplicate/traversal paths, links, special members, unsupported extensions and hidden/trailing streams are rejected. Nothing is extracted, installed or executed. Optional per-version `bundledCopies` evidence records parent identity, lock, archive URL/integrity, member path and metadata SHA-256. The introduced-version release-age check retains its independent unsupported-source gate; bundle advisory provenance does not waive package-age policy.
